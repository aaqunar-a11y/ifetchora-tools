File Hash Checker

Compute the SHA-512, SHA-384, SHA-256, SHA-1 or MD5 of a file and compare it with the checksum its publisher published — locally, without uploading anything.

Paste one hash, or a whole SHA256SUMS / checksums.txt block. A leading * marker and the trailing file name are handled for you.

    What this does not prove

    A matching hash proves one thing only: the bytes of your file are identical to the bytes that were hashed when the published value was produced. That is enough to detect a corrupt, truncated, or substituted download. It is not a statement about safety.

    • A match does not make the file trustworthy. If an attacker replaced both the download and the published checksum on the same page, the values match — and the file is still malicious.
    • It does not verify a signature. If the project publishes a .sig, .asc, or minisign file, verifying that signature is strictly stronger: it establishes who produced the file, not just that the bytes are unchanged.
    • MD5 and SHA-1 are not collision-resistant. They reliably detect accidental corruption; they must not be relied on to detect deliberate tampering. Use SHA-256 or SHA-512 unless a publisher only offers something older. Each of the five algorithms below is a different length, which is useful in itself: a 128-character value is SHA-512 and a 96-character value is SHA-384, so a pasted value whose length matches none of them is not a hash at all, and the tool says so.
    • It cannot tell you what the file is. Two different builds (x64 vs arm64, installer vs portable) can share a file name. Only the publisher's own file names and release notes distinguish them.
    • It says nothing about your device. The tool checks the file, not whether running it is a good idea.

    Notes on how it works

    Large files

    The file is read in 4 MiB slices and the hash is updated incrementally, so a multi-gigabyte installer does not have to be held in memory all at once. Progress is shown while the bytes are being read.

    Why there is no "upload" button

    There is no server component at all. Every byte is processed by JavaScript running in this page. You can confirm this by opening your browser's network panel: no request other than the page itself is made. That also means it keeps working with the network disconnected.

    Which of the five algorithms to pick

    Pick the one the publisher used, because a checksum only compares against its own algorithm. In practice that means reading the file the project ships: a SHA256SUMS line is SHA-256, a SHA512SUMS line is SHA-512, and a value copied next to the word md5 is MD5. When a project publishes several at once, SHA-256 and SHA-512 are the two worth checking — they are the strongest published here and both are still unbroken. SHA-384 is the same construction as SHA-512 with a different starting state and a shorter output, so it is equally sound but rarely published; treat it as "the publisher chose it", not as a weaker option. MD5 and SHA-1 remain useful only for spotting accidental corruption, which is the majority of real download failures.

    Why SHA-512 is implemented here rather than taken from the browser

    Browsers expose crypto.subtle.digest, which is fast, but it is only available in a secure context — and a saved file opened from disk does not count as one, so it would break the moment you use the offline copy this tool is built to provide. All five algorithms are therefore implemented in the page itself, including the 64-bit arithmetic SHA-512 needs. That is also why the page is one file with no dependencies: nothing is fetched, so nothing can fail to load.

    What the emptiness of a hash tells you

    Some publishers list a file that turns out to be an HTML page — usually a 404 page, a "quota exceeded" page, or a login redirect saved by a download manager. This tool reads the first bytes of your file and tells you when that has happened, because the hash comparison alone would only say "mismatch" and send you looking in the wrong place.
