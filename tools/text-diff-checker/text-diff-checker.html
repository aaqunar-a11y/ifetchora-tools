Text Diff Checker

Compare two blocks of text and see exactly which lines and words differ — including the invisible differences (CRLF vs LF, trailing spaces, tab/space swaps) that make a reformatted file look 100% changed.

    What this does not prove

    A line-for-line match proves that the two texts are byte-identical at the character level — nothing more. Several everyday situations make that both stronger and weaker than you might expect:

    • A match does not mean the meaning is the same. Two files can be character-identical yet describe different things if they were both produced from the same wrong source. The comparator checks bytes, not truth.
    • A match says nothing about who wrote the text. This is a diff tool, not an authorship tool. There is no fingerprinting, no metadata, and no attempt to guess the author.
    • Character-identical is stricter than visual-identical. Curly quotes vs straight quotes, an é stored as one character vs two (e + combining accent), non-breaking spaces, soft hyphens — these look the same on screen but are different code points. Text copied out of a PDF is the classic source of this kind of difference, and this page calls it out when it detects it (see the confusable-character diagnostic below).
    • The word-level highlight is a heuristic, not a guarantee. It is a best-effort refinement of a line-level result. There is no single universally correct answer to “which words within a changed line changed”, so treat the highlight as guidance.
    • It does not detect the reason for a change. The tool shows you that and where two texts differ. It cannot tell you whether the difference is a bug, an intentional edit, or a conversion artifact — you still have to read the lines.

    Notes on how it works

    Line-level vs word-level — and which one to trust

    The comparison runs in two passes. First the two texts are split into lines and compared with the Myers O(ND) algorithm, which finds the smallest possible set of line insertions and deletions that turns the original into the changed text. Each changed line is then refined word-by-word (whitespace keeps its token identity, so foo bar is two words plus a separator, not one blob). For code, trust the line-level result: a class rename inside a “changed” line is usually the real change, and word-level refinement just helps you find it fast. For prose, the reverse is often true — a reflowed paragraph changes every line while the words are untouched, and word-level shows you that nothing meaningful happened. That disagreement is not a bug; it is the two levels answering two different questions: where did the structure change and which words changed.

    Why “ignore case” and “ignore whitespace” are two separate switches

    They are different lies, and each one hides a different class of real change. Ignore case compares abc and ABC as equal — convenient for prose, dangerous for code, where a single case change (User renamed to user) can be the entire point of the diff. Ignore whitespace strips run-of whitespace before comparing — convenient when reformatting touched alignment, dangerous when whitespace is significant, as it is in Python and YAML. The two switches are independent on purpose: turning one on never silently turns on the other, and the page tells you when a switch is hiding a change.

    Where the invisible differences live

    Line endings are real characters — a CRLF file and an LF file differ on every single line even though they display identically. The diagnostic strip counts the newline styles in each input, so if a reformat flipped them you see one summary line instead of a wall of red. This is the one check that needs the file rather than a paste: a text box cannot carry a carriage return, because the browser normalises newlines in an editable element, so text pasted out of a CRLF file arrives as plain LF and the difference is gone before the tool ever sees it. Press Load file… on a side and the bytes are read as they are on disk, which is what makes the line-ending count meaningful instead of decorative. The same strip reports trailing whitespace and tab usage: trailing spaces are invisible in most editors, and a tab/space swap breaks a compare with nothing on screen to point at. Finally, the confusable-character check counts the code points most likely to arrive differently after a copy-paste through a PDF or a web page (non-breaking spaces, curly quotes, dashes, soft hyphens, combining accents) and tells you when their counts differ between the two inputs, so a difference you can see is also a difference you can explain.
